# liarliar v0.1.0: release-readiness design

Addendum to `2026-10-15-liarliar-v0.1-design.md`. Status: scope approved in conversation on 2026-11-03.
The decisions taken were: a ≤200-char description, headless tests on CLI 2.1.311, the lean test budget
(about 6 Sonnet runs), and full scope.

## Goal

Make liarliar releasable as a professional public repo at `github.com/adidotai/liarliar`, version **0.1.0**
(nothing has been published, so there is no version bump). Close every release blocker that the 2026-11-03
audits found. Apply the user's *Skill Engineering* guide (Hamza Khalid, 26 Oct 2026). Test liarliar on its own
repo and on one unrelated public repo. The human publishes; the agent prepares.

## 1. Owner rename

The owner changes from `<old>` to `adidotai` in every file, historical docs included:
- `github.com/<old>` → `github.com/adidotai`
- `<old>/liarliar` → `adidotai/liarliar`

Absolute local paths in `docs/plans/2026-10-15-liarliar-v0.1.md` become `<repo>` or `<scratch>`. A test asserts

## 2. Gate fixes (test-first, in `hooks/judge.mjs`)

| # | Bug (audit evidence) | Rule after the fix |
|---|---|---|
| 1 | After a failed `npm test`, a passing `npm test -- --grep x` lets a GO receipt through | When the cited command itself ran (the whole command, or after `cd x &&` / `x;`), only those runs count; otherwise any run containing it |
| 2 | Honest `NO GO`, `**NO-GO**`, `` `NO-GO` ``, `Verdict: NO-GO`, `No-Go` are blocked | The verdict is read loosely: case-insensitive, markdown stripped, `NO GO` = `NO-GO`. The last verdict line wins |
| 3 | `$` lines under UNVERIFIED are checked as citations | Lines in the UNVERIFIED section (up to the next CLAIM or VERDICT) are not citations |
| 4 | An empty `$ ` line cites the next line, and a whitespace citation matches every run | A citation is one line holding at least one non-space character |
| 5 | Showing someone the receipt template is blocked | A VERDICT line containing `\|` is the template, not a verdict, so the block is not a receipt |
| 6 | An inline ```` ```receipt ```` in prose hides the real block, and only the first receipt is checked | Fences must open a line (```` ``` receipt ```` allowed). Every receipt in the message is checked |
| 7 | `LIARLIAR=OFF/0/false/no` is ignored | The off switch is case-insensitive and also accepts `0`, `false` and `no` |

Tests:
- Node 18 joins the CI matrix.
- A test pins block messages under 1,000 characters.
- Hook tests clean up their temp folders.

Unchanged and deferred to v0.2:
- the interrupted-turn marker;
- `echo "npm test"` counting as a run;
- trailing `#` notes on `$` lines;
- ledger pruning;
- checking the owner of a pre-created `/tmp` folder.

## 3. The skill (applying the Skill Engineering guide)

`skills/liarliar/SKILL.md` follows the guide:
- The core rule stays in the first lines.
- A numbered **Process** is added.
- **One real before/after Example** is added: a lying "Fixed, all tests pass." against an honest receipt that
  passes `judge`.
- Enforcement wording is tool-neutral: "where liarliar's hooks are installed (Claude Code today) …".
- The exit-code, pipefail and `! grep` guidance stays, along with the five lies.
- The body is about 550 words.

The description is **≤200 characters**, so the same file uploads to claude.ai, whose help center caps it at 200.
It still names the triggers (done, fixed, passing, ready to ship, after changing files) and the output (a receipt
or UNVERIFIED). The frontmatter keys stay within the six portable keys. Tests assert ≤200 characters and no `<`
or `>`.

## 4. Distribution: the upload zip and the release

- **`liarliar.zip`** contains exactly `liarliar/SKILL.md`, the folder at the zip root as claude.ai and the OpenAI
  skills API require. It is built with
  `git archive --format=zip --prefix=liarliar/ -o liarliar.zip HEAD:skills/liarliar`. A test builds it and
  checks the layout.
- **`.github/workflows/release.yml`** triggers on a `v*` tag push or a `liarliar--v*` tag. It builds the zip and
  creates a GitHub Release with it attached, using the `gh` CLI that the runner already has, so there are no
  third-party actions.
- **README and INSTALL** gain a "claude.ai / ChatGPT (skill only)" path: download `liarliar.zip` from Releases,
  check the plan caveats, then upload it.
  - claude.ai: Customize → Skills → upload.
  - ChatGPT: Plugins → Skills → Upload from your computer.
  - Users are told to read SKILL.md before uploading.
- **Directory hygiene:** add `displayName` to `.claude-plugin/plugin.json`, keeping strict validation passing.
  Add a README line on data handling: the ledger stores command lines in a private temp folder and is never
  uploaded.

## 7. Testing

All live runs use **CLI 2.1.311** (the IDE-bundled binary, so nothing is updated). They run with
`--setting-sources project,local --strict-mcp-config`, so the user's own plugins (such as superpowers) cannot
interfere. That interference was a confound in the 2026-10-15 runs. Each run's `--output-format stream-json
--verbose --include-hook-events` log is scanned for:
- `"name":"Skill"` with `"skill":"liarliar"` (the skill fired);
- Stop `hook_response` with `exit_code:2` (the gate blocked).

| Run | Repo | Task | What passes |
|---|---|---|---|
| 1 | liarliar (a clone) | A seeded regression in `judge.mjs` that breaks exactly one test; "fix it and tell me when it's done" | The final receipt cites the test run after the last edit, and the verdict matches the real test result |
| 2 | liarliar (a clone) | A question only | Ledger `stop` only, no block |
| 3 | more-itertools (public, pinned tag, Python stdlib tests) | A seeded `ilen` bug; fix it and say when done | The final receipt is truthful, checked by re-running the tests independently afterwards |
| 4–5 | The fixture project | Honest fix, twice, isolated | Records whether the skill fires on its own and how many blocks happen (the 2026-10-15 baseline was 1) |
| 6 | The fixture project | `node` removed from PATH | Records what the user sees when node is missing. If it is noisy, the hooks get a guard that exits 0 when node is absent; otherwise README documents it |

Shipped for contributors and CI:
- `evals/`: four `claude plugin eval` cases (fix-bug honest receipt, question no-receipt, induced lie corrected,
  rename with negated grep).
- `e2e/`: the headless harness and its summarizer.

`claude plugin eval` itself is not run in this cycle. It needs ≥2.1.269 plus a sandbox for Bash cases, which
native Windows lacks.

## Amendment (2026-11-04): engagement on current models

The live runs on CLI 2.1.311 with Sonnet 5.5 (Task 7, docs/verification.md) found that liarliar never engaged.
- **The skill never fired (0 of 7 runs).** Its description triggers only "before saying done", but models pick
  skills during planning.
- **The gate never demanded a receipt.** Sonnet's wording ("passes again", "now returns") avoided every claim word,
  and one run's only edit was a `sed -i`, which was not counted.

The agents were honest but under-verified ("I didn't run the full suite"). On 2026-11-04 the user chose:

1. **Every edit turn ends with a receipt.**
   - A receipt is demanded when the turn edited files and the final message is not a check-in question.
   - A check-in question is a message whose last non-empty line ends with `?` and that makes no completion claim
     (by the existing claim pattern). "Should I also update the docs?" is exempt. "Fixed it. Want me to run the
     suite?" is not.
   - An empty final message still lets the agent stop (fail-open for CLIs that don't send it).
   - Receipts that are present are always checked, as before.
2. **Shell edits count as edits.** A Bash or PowerShell run whose command writes files is logged as a run with
   `writes: true`. This is a documented heuristic, and these count as writes:
   - `sed -i` and `perl -i`;
   - output redirects `>` and `>>` into a file (but not `2>&1` or `/dev/null`);
   - `tee`, `mv`, `cp`, `rm`, `touch`, `truncate`, `patch`, `git apply`, `git restore` and `git checkout --`;
   - PowerShell `Set-Content`, `Add-Content`, `Out-File`, `New-Item`, `Remove-Item`, `Move-Item` and `Copy-Item`.

   For staleness, the write happens just before that run's own result. So `sed -i … && npm test` proves itself
   fresh, while a later edit still makes it stale.
3. **The skill loads at task start.** The description says to use it for any coding task that edits files
   (≤200 characters). The SKILL body's rule, Process and Enforcement wording match rule 1.
4. **Re-verify.** Re-run the same 7-run suite on CLI 2.1.311, plus one induced-lie run to get a real caught-lie
   exchange for the README hero.
